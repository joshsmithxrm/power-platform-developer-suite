and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

## [1.5.0] - Unreleased

### Added

- **Bounded cloud-flow activation** - `flows enable` and `flows disable` accept one ID/unique name or all eligible definitions in a named solution. Write-free plans report blockers, exclusions and a plan hash; execution verifies per-flow outcomes and retains partial or uncertain results without blindly retrying submissions. `--max-flows` defaults to 100; `--timeout` defaults to 60 seconds per flow (#1214).
- **Shared target acknowledgement** - existing form mutations and new flow writes use a resolved-context service guard. Protected targets require `--confirm-env <resolved-url>`; read-only sessions reject the covered writes (#1015, partial).
- Optional `data export --max-records-per-entity` bounds primary rows per entity. Exceeding the positive limit fails before writing output instead of truncating. Bounded mode requires paging cookies and refuses, before exporting, a schema with relationships or file, image or binary columns and an entity filter that is not plain `filter`/`condition`/`value` FetchXML; the default remains unlimited (#1575).
- `plugins diff --include-hidden` also compares hidden steps. Without it hidden steps are excluded and the comparison is reported as incomplete (exit 12) (#1524, #1605).
- **Breaking: exit code 12 (`Incomplete`)** - the check could not be completed, so the result is unknown (neither match nor drift). `plugins diff`, version 2.0 `plugins deploy` post-deploy verification and schema-delete dependency checks now exit 12 when incomplete; earlier builds of this release exited 2, the same code as a general failure. For schema delete this applies to `--dry-run` and to a real delete that is refused, and a blocked refusal exits 10 on every path (the service-side recheck after confirmation previously exited 2 for both blocked and incomplete). Match (0), drift (1) and failures keep their codes; JSON output, status strings, error codes and messages are unchanged. A script that treats exit 2 from these commands as "could not compare" must test for 12 (#1605).
- `ppds forms repair-bindings --entity <table> --form <name-or-id>` rewrites control bindings (`datafieldname`) in a Main form's layout (tab sections, tab headers/footers, form header/footer) that differ from a column's logical name only by case, to the exact logical name. It sends the stored form XML text with only those values replaced, then reads the unpublished form back and checks each rewritten control before any `--solution` or `--publish` step. Reported and left unchanged: control ids, bindings that match no column or several, relationship and unbound controls, controls outside the form layout, and case-variant names in custom-control parameters, form events and hidden controls. `--dry-run` only reads and cannot be combined with `--publish` or `--solution` (exit 3). Protected targets require `--confirm-env`. Errors say which step failed and what was already written. CLI only; there is no MCP tool (#1527, #1606).
- `forms add-field` JSON output gains `addedControls` (`[{field, controlId}]`), the control id written for each new placement. Existing keys are unchanged (#1601).
- **Explicit field resets** - a `resetFields` list on a step or image in the registration file, and `--reset-fields` on `plugins register step` and `plugins register image`, clear the named optional fields on update. Steps accept `filteringAttributes`, `unsecureConfiguration`, `description`, `runAsUser`, `asyncAutoDelete`, `canBeBypassed` and `canUseReadOnlyConnection`; images accept `attributes` and `description`. A field cannot be both given a value and listed for reset, and `secureConfiguration` cannot be reset. Under version 1.0 this is how a file clears a property: remove it and list it in `resetFields` (#1519, #1524).

### Changed

- Native release executables use self-contained .NET 10.0.15, retaining all five platform targets. NuGet libraries and CLI/MCP tool framework assets remain unchanged. Linux native glibc minimum is 2.27; OS vendor support is a separate requirement. Native and VSIX candidate artifacts receive source/runtime/extraction checks before release.

- Every existing `--environment` option also accepts `-env`. Existing `-e` meanings remain unchanged; entity/entity-list uses emit one value-free deprecation notice on stderr and help recommends `--entity`/`--entities`. Use `-env` or `--environment` to select an environment unambiguously (#1536).
- Schema-delete previews read unpublished target identity and deletion dependencies. Blockers exit 10 and incomplete checks exit 12, with retained component identities; actual deletion rechecks after confirmation and refuses with the same codes (#1605). Read failures retain safe auth/timeout recovery codes and original internal causes. Other metadata dry-runs state their completed checks and provisional/unallocated values while preserving existing JSON data fields. A clear preview does not establish server delete feasibility (#1532).
- Legacy `forms reorder-fields` is deprecated, with a stderr-only warning and unchanged JSON shape. Use `forms reorder-fields-strict`, `forms add-field` or `forms move-field` instead. It retains authoritative add/drop behavior but now rejects repeated inputs, ambiguous selected bindings and silent cross-section copying.
- `forms reorder-fields-strict` permutes existing fields without additions/removals; `forms move-field` relocates an existing cell with preserved IDs, authored labels and nested content. Unsafe/ambiguous layouts fail before a final single XML update; explicit solution/publication remains separate.
- All nine existing `views` writers now enforce the shared target-confirmation policy. Scripts targeting protected environments must pass `--confirm-env <resolved-url>`; read-only sessions reject writes, including no-op edits. `views list` and `views get` remain acknowledgement-free. The original four-argument `ViewService` constructor remains available for readers, but direct writers must supply a resolved confirmation service (#1015, partial).
- When `--confirm-env` is required because the environment has no saved type, the error now adds that the environment is treated as Production and gives the `ppds env config <url> --type <type>` command that records it. The error code and the rest of the message are unchanged (#1533).
- Help no longer lists a short alias on `--output-format` or `--verbose` where the command's own option already owns it, for example `-f` on `plugins unregister` (`--force`) and `-v` on the `views` commands that take `--view`. Which option each alias selects is unchanged on every command. Guard tests now fail when a new short-alias clash is added (#1536).
- `plugins deploy`, `clean` and `extract` help describes registration versions 1.0 and 2.0 and how secure configuration is handled. A deploy dry-run, for every registration version, now ends with "Dry-run complete (planned, not performed)" instead of "Deployment complete" (#1519).
- Under registration version 2.0, the orphaned-step warning from `plugins deploy --clean` and `plugins clean` gives each step id and `ppds plugins unregister step <step-id>`, and says deploy verification reports drift (exit 1) until the step is removed. Steps are still never deleted under 2.0 (#1519).
- For 1.0 or unversioned registration files, `plugins diff` and `plugins deploy` (real and dry-run) print a stderr notice and add an additive `preservedLegacyValues` JSON field listing omitted properties whose stored value differs from what version 2.0 would write, with how to adopt 2.0. The notice is computed after the writes and cannot change what is written or the exit code. Unsecure configuration values are shown as `(redacted)` (#1519).
- **Breaking for registration files with same-named images on one step (1.0, unversioned and 2.0 alike):** when a step in the registration file lists two images whose names are equal ignoring case, `plugins deploy`, `plugins diff` and version 2.0 `plugins clean` refuse it before connecting (exit 3). The message names the step and the images and, for a same-named pre-image and post-image, suggests one entry with `imageType: "Both"`. Such a file used to deploy with exit 0 while the second entry silently overwrote the first; it is now rejected and nothing is deployed. Version 1.0 `plugins clean` does not pair images and is unaffected. `plugins extract`, which does not connect, runs this check only when it merges into an existing registration file (the output file already exists and neither `--force` nor JSON output is used): it then refuses a plugin whose `[PluginImage]` attributes give one step two image names equal ignoring case, and refuses to merge an extracted image that matches several case-variant images in the existing file without one exact-case match (exit 3). A first extract, `--force` and JSON output do not run the check, so they can write a file that `plugins deploy` and `plugins diff` then refuse (#1603).
- When stored images on one step have names equal ignoring case: if a configured image has that name, `plugins diff` reports the step incomplete (exit 12), naming the images, their IDs and `ppds plugins unregister image <image-id>`; if none does, they are ordinary orphaned images (drift, exit 1). In both cases `plugins deploy --clean` and `plugins clean` refuse before any change (exit 3), naming the images and IDs (#1603, #1605).
- When version 2.0 deploy verification does not match, text-mode `plugins deploy` lists on stderr what drifted (property names only, no values) and any unverifiable items, then points to `ppds plugins diff`. JSON output is unchanged (#1603).
- `forms add-subgrid` refuses (`Forms.DuplicateSubgridName`) a generated `subgrid_<label>` name that another control on the form already uses as its id; it previously wrote a duplicate id (#1601).
- **Breaking:** `optionset update-option`, `attribute update-option` and `entity update-statusreason` with nothing to change (neither `--new-label` nor `--color`) fail with `MISSING_REQUIRED_FIELD` (exit 8) before connecting, instead of reporting success (exit 0) (#1604).
- **Breaking:** new error code `WRITE_NOT_CONFIRMED` (exit 2): the write returned success but a label, description or option colour it carried could not be confirmed by reading it back, or is stored differently from what was sent. Every metadata label write is read back as-if-published before success is reported and before `--publish`: table, column (including local option labels and Boolean true/false labels), lookup, alternate-key and global-choice creates, and table, column, choice, option, status-reason and state-value updates. A read-back that fails, times out, is cancelled after the write, or returns no metadata uses this code too. The message says what was written, which label was not confirmed (requested and stored text) and that `--publish` was not attempted; a create that fails this way did create the object. `requiresReauthentication` is kept in the error context. Read-back failures that used to surface as `OPTION_NOT_FOUND` (exit 8), `Connection.Timeout` (exit 4) or an authentication failure (exit 5) now use this code (#1604, #1699).
- **Breaking (public API of the CLI tool assembly):** `IMetadataAuthoringService.UpdateTableAsync`, `UpdateColumnAsync`, `UpdateGlobalChoiceAsync`, `UpdateOptionValueAsync`, `UpdateStatusReasonAsync` and `UpdateColumnOptionAsync` now return `Task<MetadataLabelWriteResult>` instead of `Task`, carrying label notices such as `BASE_LANGUAGE_LABEL_ONLY`. A custom implementation no longer compiles, and a caller compiled against the old signatures must be rebuilt (#1604). Additive: `IFormService.RepairBindingsAsync` has a default implementation (#1606), and `AddFieldsResult.AddedControls` is a new property (#1601).
- `SDK_OPERATION_FAILED` no longer implies that nothing was written: a timed-out or cancelled option or status-reason insert says its outcome is unknown and how to check before retrying. A publish failure after a written option keeps its code and exit and says the change is saved but not published (#1604).
- **Breaking on organisations whose base language is not English:** metadata labels are written in the organisation's base language (`organization.languagecode`) instead of always in English (LCID 1033): creating and updating tables (display name, plural name, description and the primary name column), columns (including Boolean true/false labels and local options), lookups, alternate keys, global choices and their options, status reasons and state values, on the CLI, TUI, MCP and RPC. Nothing changes on an English-base organisation. On another base language, label updates no longer exit 0 having written nothing or having overwritten the base label while saying it was unchanged, and adding options and status reasons no longer fails with fault `0x80044195` ("The language code 1033 is not a valid language for this organization"); all three were observed on a French-base organisation. Labels in other languages are kept. The base language is read from the organisation when a label is about to be written (once per environment for a TUI or daemon session, once per CLI command, once per MCP tool call); if it cannot be read the command fails before writing anything. The help for every label option says "(in the organization's base language)". When the label Dataverse shows the caller is a stored label in a language other than the base language and differs from the new text, option (label and description), status-reason, choice, table and column label updates warn that only the base-language label changed, naming both LCIDs (stderr `Warning:`, rule `BASE_LANGUAGE_LABEL_ONLY` in additive JSON `data.validationMessages`; also reported through MCP, RPC and the TUI); the exit code is unchanged. The notice was named `ENGLISH_LABEL_ONLY` earlier in this unreleased version. A table label update reads the table first and keeps its auth, connection and timeout exit codes. In the TUI, a create whose labels could not be confirmed is reported as created but not confirmed, and the list is reloaded (#1604, #1699).
- Input-only dry runs of `optionset update`, `optionset add-option`, `attribute create` and `column create` with a global choice name say that the name was not looked up (additive `metadata.preview.globalChoiceNameChecked: false`) (#1604).

- Refreshed System.CommandLine 2.0.9 to 2.0.14, Nerdbank.Streams 2.13.16 to 2.14.411 and direct Microsoft.Extensions dependencies to 10.0.14; consumed the coordinated Auth/Dataverse/Migration/Query/Plugins releases and their JWT/build-tool servicing (#1499, #1500, #1501, #1502), including MSAL 4.92.0 and System.Text.Json 10.0.14 (#1513, #1565).
- `schemas/plugin-registration.schema.json`, the `$schema` that `plugins extract` writes, now models registration versions 1.0 and 2.0, `resetFields` and the per-version omission rules, with descriptions and enums for the documented values. Validating existing files against it may now report a `version` other than `1.0` or `2.0` (the CLI also rejects those before connecting) and, for version 2.0 files, any property the schema does not define. Version 1.0 files still allow additional properties.
- **Compatibility exception for this release only** - Josh approved CLI 1.5.0 and MCP 1.3.0 on 2026-11-01 despite stricter protected-write behavior and incompatible CLI/MCP implementation signatures. Update scripts with required acknowledgements and custom embedders with the documented signature changes. This is not a blanket backward-compatibility claim or a permanent version-policy waiver; see the [scoped exception and migration guide](https://github.com/joshsmithxrm/power-platform-developer-suite/blob/main/docs/releases/v1.8.0.md#one-release-compatibility-exception).

### Fixed

- Direct plugin image updates preserve omitted registration values and use Dataverse row-version checks. Concurrent edits or unavailable capabilities fail without automatic mutation retries; acknowledged updates remain distinguished from connection-cleanup failures. RPC callers receive the service's structured codes and safe outcome warnings without private diagnostics.

- Version 2 image-only cleanup also refuses present-null step/image protection metadata during planning and fresh pre-dispatch checks. Public DTO bool values/signatures remain; the checks do not make deletion atomic.

- Plugin image cleanup refuses incomplete parent protection metadata and hidden assemblies; explicit `IncludeHidden` inventories include hidden rows. Malformed protection fields in the selected SDK Get responses now return a fixed coded error instead of implying an unmanaged component.

- Registration version 2.0 `plugins clean` and `plugins deploy --clean` now use an explicit image-only plan on uniquely owned configured steps. Every configured step must supply `images` (including `[]` to clear); omitted/duplicate lists cannot grant delete authority. Plans retain exact parent/image IDs, inventory counts and acknowledged/unknown outcomes; new/unplanned images and all parent registrations remain. Version 1 keeps its established legacy parent cleanup. Ownership rechecks do not provide atomic conditional deletion or imply rollback (#1519).
- Preserve explicit zero while allocating only omitted local/global choice values, without mutating caller options. Global --options accepts bare labels; explicit values outside the publisher range warn and remain unchanged (#1530). For automatic allocation, omit Value rather than setting it to zero. Initial create previews mark derived values as provisional without claiming target-option reads or persisted numeric output.


- `forms move-field` refuses source-row removal and target-row insertion across active row spans, and refuses shifting a later spanning sibling. Safe mixed rows, expired spans and unchanged-position retries remain supported.
- Repeating `forms add-field` in the same section preserves existing controls/custom labels and skips redundant XML updates. Casing and batch duplicates report accurate already-present and duplicate-input outcomes; intentional placements in other sections remain supported (#1528).
- New cells created by legacy form reorder use metadata display labels and canonical bindings; existing custom labels are retained. The additive result API keeps the original Task-based add-field signature and reports unknown counts truthfully for legacy implementations (#1529).
- Plugin deploy preview reads existing image inventory and distinguishes reused types (#1517). Registration version 2.0 explicitly opts into supported nonsecret desired-state defaults and read-only post-write verification; missing/version 1.0 retains legacy optional preservation. Established Update empty-string clears are preserved (#1519).
- Plugin diff compares managed execution/image settings and reports incomplete coverage with exit 12. In 1.4.2 diff exited only 0 (no drift) or 1 (drift), or 2 and above for errors. Exit 12 means the comparison was incomplete; exit 2 remains a general failure and returns an error object with no `metadata`. `metadata.status` (`match`, `drift`, `incomplete`) is also available (#1605). Existing JSON `data[]` remains; additive `metadata` contains status/coverage. Secure values are unverifiable and excluded; unsecure configuration differences are redacted (#1520).
- Registration preflight validates configured user identities before artifact upload. Scoped configuration/output codecs preserve generic model intent and write-only inputs; extraction supports explicit --registration-version and now writes explicitly declared `deployment`, `invocationSource`, `canBeBypassed` and `canUseReadOnlyConnection` values, including defaults, instead of dropping them. Version 2 fresh defaults take precedence over legacy overlays. Original update-record constructors/deconstruction and positional RPC targets remain compatible.
- `views reorder-columns` now requires every existing column exactly once and rejects empty, partial, unknown or duplicate names before writing. Reordering preserves cell metadata and other layout content; use `views remove-column` for removal (#1533).
- Form `add-field` and newly created `reorder-fields` controls use the resolved metadata logical name for bindings, and as the control ID, regardless of input casing (a repeated placement gets a suffixed ID; see the #1601 entry). Existing controls and label behavior are preserved; invalid new-field requests are rejected before writes even for sections without rows (#1527).
- Form XML raw get/set roundtrips accept repeated reusable `customControl` type IDs at their schema-defined path. Instance GUID uniqueness and schema validation remain enforced; set-xml help now distinguishes instance IDs from reusable type IDs (#1541).
- A cancelled option-colour read-back, which now runs after the write that carried the colour, is reported as `WRITE_NOT_CONFIRMED` (CLI exit 2) with the original cancellation as its inner exception; the message states what was written (#1604). Normalize connection checkout failures in the bounded metadata workflows and shared prefix/publication helpers with their original mapped CLI exits and causes. Prefix checkout normalization also applies to existing table, column, one-to-many/many-to-many relationship, global choice and key creation callers. MCP option-add now reports Connection.Timeout for pool exhaustion (CLI exit 4 remains). Other direct column acquisitions, catalog read behavior, SDK execution contracts and partial-operation limits remain; the bounded diagnostic-message change is documented below.
- Return the table-update connection before cache invalidation and optional publication, allowing an update followed by publication with one available pooled connection. Existing payload, dry-run and SDK contracts remain; scoped checkout normalization is listed above. Separate requests can still complete partially after a later failure.
- Return metadata authoring connections before option-color or publication follow-ups, and use separate connections for the colour read-back and publisher-prefix queries. This lets the covered option/status/table-create workflows complete with one available pooled connection. The scoped cancellation and acquisition changes are listed above; separate requests can still complete partially if a later operation fails.

- `metadata attribute update` (and the deprecated `column update`) can change the display name and description of State, Status and unique-identifier (GUID) columns, including a table's primary ID column. Only the labels are sent; any other setting on these columns is rejected with `INVALID_CONSTRAINT` (#1550, #1559).
- `flows list` pages through all results, and with `--solution` it matches only workflow-type solution components. `flows get <name>` fails with a validation error (exit 3) that lists the matching ids when more than one flow has that unique name, instead of returning the first match (#1495).
- Plugin deployment retains earlier step errors when a later operation fails, and secondary-only message-filter diagnostics identify the actual secondary-entity requirement (#1360).
- Plugin diff propagates cancellation through every drift-collection and comparison stage (#1317).
- Web-resource creation reports missing or mismatched publisher-prefix warnings in structured results and stderr without renaming the resource. Missing-resource update guidance uses the literal `<file>` placeholder (#1236).
- Query RPCs and history retain the captured authentication identity and executed environment during concurrent profile/environment changes (#1218).
- Form tab/section selectors prioritize stable IDs and reject ambiguity while retaining unique legacy GUID-valued name selectors. Form listings page all results, inspection includes draft hash/state, and operation cancellation propagates accurately.
- Plugin updates respect readable/createable/updateable field capabilities: omit already-equal non-updatable values and refuse requested mismatches before other mutations. Direct invocation-source updates verify persistence. Package targeting refuses ambiguous identities and reads package bytes from the Dataverse file column (#1572, #1573, #1581).
- A supplied `secureConfiguration` is write-only and never read back. `plugins diff` lists it under `coverage.excluded` ("supplied but not compared"); it does not make the comparison incomplete and does not affect the exit code, and a successful version 2.0 `plugins deploy` that supplies it exits 0. As in 1.4.2, the secure value is not compared. No secure value is printed (#1520).
- `plugins diff` on 1.0 or unversioned files reports a stored step `filteringAttributes` or image `attributes` that the file omits, or sets to null or empty, as drift (exit 1), as CLI 1.4.2 did. Guidance printed once per run on stderr, and in the JSON `warnings` of each affected assembly, explains how to resolve it. Other omitted properties are listed in the advisory notice, not compared (#1519, #1520).
- `plugins deploy --dry-run --clean` and `plugins clean --dry-run` under version 2.0 list each image that would be deleted and show the correct planned count in text output. JSON output is unchanged (#1519).
- `forms add-field` reports when a field it adds already exists in another section, tab, header or footer (stderr notice and additive `otherPlacements` JSON field). `forms add-field` and legacy `forms reorder-fields` warn when an existing control's binding differs from the column logical name only by case (additive `nonCanonicalBindings` JSON field). Neither command rewrites an existing control; the warning points to `ppds forms repair-bindings` (#1527, #1528, #1606).
- Global choice names that differ from the stored name only by case now work on `metadata optionset <name>`, `optionset update`, `add-option`, `update-option`, `remove-option`, `reorder`, option colour and the delete preview, as well as on column create (#1552). In 1.4.2 a mis-cased name failed as not found on all of these. The exact name is tried first; the stored name is looked up only when Dataverse reports the option set as not found. Other errors and existing not-found results are unchanged. On the write commands and the delete preview, a name that matches several stored names by case fails with `INVALID_CONSTRAINT`; the read (`metadata optionset <name>`) keeps its not-found result in that case. Recognition checks the Dataverse fault code `0x80040217` first and falls back to the English server message. That fault code was observed live for a mis-cased and for an unknown global choice name on an English-base and on a French-base organisation, with the message text in English on both (#1535, #1604, #1699).
- `optionset delete` shows the stored name when the typed casing differs and, when it prompts, asks for `DELETE OPTIONSET <stored name>`. With `--force` it deletes the stored-name object without a prompt. It reports the stored name in `name` and the typed name in a new `requestedName` JSON field, and, just before deleting, rechecks that the choice is still the previewed object and refuses if it was renamed or recreated. The recheck and the delete are separate requests, so a change made between them is not detected (#1535).
- Status-reason and choice-option update/remove can target an option that was added but not yet published. Targeting by `--label` is refused when the published and unpublished labels disagree about which option it means, including on `optionset update-option` and `remove-option`; `--value` is unaffected. Global option colour applies to just-added options. Failures show the Dataverse fault code, and a cancelled update/remove is reported as cancelled (#1531).
- For Choice columns, legacy comma-separated `--options` on `attribute create` and `column create` accepts bare labels (values allocated as with `--option`) and rejects malformed entries instead of dropping them. On `attribute create` for Choice and Choices columns, using more than one of `--option`, `--options` and `--options-file` is a validation error; other column types keep the earlier first-source-wins parse. `optionset add-option --dry-run` marks an omitted value as unallocated (#1530).
- `--color` on an existing option now sets its colour (`optionset add-option`/`update-option`, `attribute add-option`/`update-option`, `entity add-statusreason`/`update-statusreason`). The colour is sent as the `Color` parameter on the same insert or update request as the label and read back afterwards; it is passed to Dataverse exactly as given. Since CLI 1.2.0 the colour had been sent through `OptionMetadata.Color` on `UpdateOptionSet`/`UpdateAttribute`, which Dataverse accepts and ignores, so the 1.2.0 entry "Option colors now persist" was wrong for options that already existed; colours set when creating a choice or column were not affected. A colour cannot be cleared through these commands (#1604).
- `optionset update` reads the choice as-if-published before re-sending it, so it no longer reverts an unpublished edit to a property the caller did not change (#1604).
- Option, status-reason and state-value updates send a label only when a new one is requested, so a colour-only update no longer rewrites the label. Label writes on these and on table and typed-column updates set `MergeLabels`, so labels in other languages are kept (unit-tested, and since asserted live on an English-base organisation with French provisioned; in full runs of that live suite one test stopped in its own setup before reaching its check, #1760) (#1604).
- Empty or blank solution names are sent as no solution on option requests; Dataverse rejected `""`. Removing or reordering options refreshes cached metadata without `--publish` (#1604).
- `plugins diff`, version 2.0 deploy verification, deploy's create/update counts (including `--dry-run`), the 1.0 preserved-value notice and `plugins extract` merging pair a configured image with a stored image by name ignoring case, the rule image writes and cleanup already used. A case-only difference is reported as a `name` change (not a missing plus an orphaned image), counted as `imagesUpdated` rather than `imagesCreated`, and corrected in place by deploy (#1603).
- When several stored images match a configured name ignoring case, the image write updates the exact-case image first, otherwise the earliest created, then the lowest ID, regardless of server order (#1603).
- `data export --max-records-per-entity` help says that schemas with relationships or image, binary or file columns, and non-plain filters, are refused before export starts; it previously said bounded mode "disables" them (#1603).
- `forms add-field` no longer writes a second control with the same `id` when a column is placed in more than one section, or is already on the form (header and footer included) under its bare name. The new placement gets `<column>N` with the smallest free N, skipping any number that is another column's logical name on the table; comparison ignores case. Existing controls are never renamed. New cells created by legacy `forms reorder-fields` follow the same rule; `move-field` and `reorder-fields-strict` keep existing ids. A script can observe a different `id` for a new control only when the bare logical name was already in use (#1601).

### Security

- Sixteen metadata SDK/catalog failure paths now report fixed action and target context without appending provider diagnostics. CLI error codes, exit codes and original inner causes are preserved; scripts should use error codes rather than SDK message text. This is bounded to the named authoring paths, with no general log-redaction guarantee.

### Validation

- Bounded/configurable live propagation polling and verified fixture-owned cleanup retain useful failure evidence; background update-check regressions use controlled time and explicit completion instead of sleeps (#1314, #1361). These are validation improvements, not new runtime timeout settings.
- Relevant Python workflow regressions feed the required, always-reporting `test-status` gate (#1357). Managed-form fixtures, live roundtrips and cleanup provenance complement retained managed-view coverage (#1240).

## [1.4.2] - 2026-10-30

### Security
- **Plugin reference caches are isolated by OS account** — embedded framework references now use protected local application data and validate ownership, permissions and links before reuse or repair. Unsafe storage, including mutation-capable macOS ACLs, is rejected with a path-specific warning; use the [cache troubleshooting guidance](README.md#command-structure) to restore safe storage. Legacy shared-temp caches are neither used nor removed. This boundary does not protect against same-account or administrator mutation or hostile filesystems (#1329).
- **Runtime security dependencies refreshed** — include `System.Security.Cryptography.Pkcs` 10.0.13, `System.Security.Cryptography.Xml` 8.0.5, and MessagePack 2.5.307 through StreamJsonRpc 2.26.150 (#1462, #1470).

### Fixed
- **Unsupported plug-in package guidance now qualifies the loose-assembly alternative** — a loose DLL must still target a supported .NET Framework version and be strong-name-signed; repackaging alone does not make netstandard or modern .NET targets deployable.
- **Plugin extraction repairs incomplete reference caches** — the embedded .NET Framework reference cache now checks every expected file and its size, restoring missing or truncated facades such as `System.Runtime.dll` even when `.complete` and `mscorlib.dll` survive. Readers inspect trust and completeness under the repair lock, avoiding failures from a concurrent replacement. Complete caches are reused without rewriting (#1358).
- **Forms writes accept Timeline activity configuration** — the bundled schema now recognizes `UClientActivitiesConfigurationJSON`, allowing direct XML writes and unrelated structured edits to preserve standard Timeline settings while retaining structural and parameter type validation (#1465).
- **Model-driven app editing preserves intended selections and localized navigation** — all component names/IDs are validated before writes, duplicate names require explicit candidate IDs, retained selections are kept, and additions precede removals with partial-failure guidance. Sitemap matching resolves localized labels, prioritizes stable IDs, rejects ambiguous titles and preserves translations (#1448).
- **View column and draft verification correctness** — direct columns now synchronize and repair FetchXML projections; related columns use distinct alias-qualified layout names and valid attributes. ### Fixed
- **`ppds metadata optionset update-option|remove-option --label` no longer silently targets the wrong option on duplicate labels** — duplicate option labels are legal in Dataverse, but the authoring service resolved a `--label` selector with a first-match lookup, so `update-option`/`remove-option` could mutate or delete whichever matching option happened to come first. Label resolution now collects every match and, when more than one option shares the label, throws `MetadataAuthoring.AmbiguousOptionLabel` listing all matching values and directing the user to disambiguate with `--value`. The same guard is applied to the attribute-local choice path (`attribute update-option|remove-option --label`) and the status-reason paths (`entity update-statusreason|remove-statusreason --label`). Single-match and no-match (`OPTION_NOT_FOUND`) behavior is unchanged (#1235, regression from #1229).
- **`ppds forms set-xml` now completes the modern-form round-trip** — after #1203/#1206 unblocked the schema gate, the very next gate (`FormXmlValidator.ValidateGuids`) still rejected real Microsoft model-driven forms with `Form XML contains a non-brace-format GUID 'fullname' on attribute 'id'`. The custom check was wrong two ways: its logical-name exemption covered only `<control>.id`, but real forms also carry logical names on `<data>.id` (e.g. `fullname`) and `<dependency>.id` (e.g. `absoluteurl`); and it demanded brace-wrapped GUIDs, while real forms use valid *unbraced* GUIDs (e.g. on `<section>.id`). The bundled XSD already validates GUID format correctly — `FormGuidType` accepts braced and unbraced GUIDs (`\{?...\}?`) and types logical-name ids as `xs:string` — so the hand-rolled format check was a redundant reimplementation that had drifted out of sync with the schema. It is removed; the XSD is now the single source of truth for format, and `ValidateGuids` keeps only the one thing the schema cannot express: cross-element GUID uniqueness (over GUID-valued ids, brace-normalised). Completes the modern-form `set-xml` round-trip started by #1203/#1206 (#1209).
- **`ppds forms` write commands no longer fail on modern UCI forms** — `forms set-xml` and the structured `add/update/remove tab|section|field|subgrid` editors re-validate the whole form document against the bundled `FormXml.xsd` before writing to Dataverse. The root `<form>` element's type was a closed attribute allowlist with no `xs:anyAttribute`, so the `headerdensity` attribute Microsoft added to modern model-driven (UCI) Main forms (e.g. `headerdensity="HighWithControls"`) was rejected with `The 'headerdensity' attribute is not declared`. The schema now declares `headerdensity` and accepts unknown `<form>` attributes leniently (`xs:anyAttribute processContents="lax"`) so future server-side additions no longer hard-fail valid forms. GUID/control-id validation is unchanged (#1203).
- **Reliable view writes** — `ppds views set-fetchxml|set-filter|clear-filter|set-sort|clear-sort|reorder-columns|update-column|remove-column` no longer fail opaquely or report a false success, and now succeed on managed views. Every fetchxml- and layoutxml-mutating command routes through one shared verified write path that (a) surfaces the underlying Dataverse fault (e.g. `0x80040216`) instead of the bare `Details: setting fetchxml`; (b) echoes `returnedtypecode` into the savedquery write so the platform applies fetchxml changes — the missing entity context was the actual cause of `0x80040216`; (c) verifies the change persisted via a lag-tolerant read-back against the *unpublished* record (`RetrieveUnpublishedMultiple`), so a draft write is no longer falsely reported as `View.UpdateNotPersisted`; and (d) reserves the `View.ManagedComponentNotEditable` error for genuinely locked components (`iscustomizable = false`) instead of refusing all managed views. Live-verified against a managed Quick Find view (#1190, #1194, #1200, #1201).
- `ppds model-driven-app set-views|set-forms|set-charts` with explicit named components no longer fail with `Input field type 'EntityReference' does not match expected type 'Guid' for field 'AppId'`. The shared `AddAppComponents` helper now passes the appmodule id as a `Guid` (matching the working `RemoveAppComponents` sibling); a regression test asserts the request parameter type (#1183).
- **`ppds forms`/`ppds views` mutations no longer silently overwrite earlier unpublished edits** — every mutation now reads the *unpublished* record (`RetrieveUnpublishedMultiple`) before writing, so successive edits compose instead of the later write clobbering the earlier one off a stale published read. Forms additionally detect non-customizable forms up front and throw `FormNotCustomizable` (Dataverse accepts the update but never persists it), and layout mutations against views with no `layoutxml` throw a clear `View.NoLayout` instead of a cryptic `0x80040216` (#1243).
- **`ppds model-driven-app add-table`/`remove-table` now work on draft (never-published) maker apps** — the sitemap is resolved by `sitemapnameunique == appmodule.uniquename` (and reads use `RetrieveUnpublishedMultiple`), so edits patch the maker's existing sitemap instead of minting a second one that Dataverse rejects with `0x80050111` ("App can't have multiple site maps"). Table membership is also registered under the table's own logical name rather than the literal `"entity"`, which had registered a spurious "Entity" component (#1242).
- **`ppds metadata attribute create --type DateTime` with `DateOnly` behavior no longer rejected** — `BuildDateTimeAttribute` now sets `Format=DateOnly` automatically when the behavior is `DateOnly` (Dataverse rejects a `DateOnly` behavior paired with the previous default `DateAndTime` format) (#1244).
- **`ppds publish` surfaces environment-lock faults with actionable guidance** — when Dataverse rejects a publish because another import/publish is already running, the error now states that your edits were saved and to retry once the environment is idle, instead of a raw fault. `ppds publish --type entity --solution <name>` without explicit entity names is also rejected up front with a clear message (#1245).
- **Option colors now persist** — color writes route through `OptionMetadata.Color` re-sent via `UpdateOptionSet` (global choices) / `UpdateAttribute` (local column options and status reasons) instead of the `request["Color"]` indexer, which the Insert/Update OptionValue SDK messages define no parameter for and silently drop. Local-option color updates send a minimal carrier attribute so unrelated attribute-level managed properties (e.g. `RequiredLevel`) are not reset (#1233, #1234).
- **`ppds metadata column update` now persists `RequiredLevel` changes and signals the publish requirement** — the service sends a fresh, minimal `AttributeMetadata` (copying only the requested fields) instead of retrieve-then-mutate, which the SDK silently drops `RequiredLevel` from; the success message (and JSON `requiresPublish`/`publishHint`, MCP `RequiresPublish`/`PublishHint`) now tells the user to run `ppds metadata publish` for the change to take effect (#1009).
- **`ppds custom-apis register` validates nested parameters** — `uniqueName`/`displayName`/`type` on each nested parameter are validated up front with `RequiredField` (naming the offending index), matching `add-parameter`; a null list element is rejected explicitly instead of throwing `NullReferenceException` (#1228, #1230).
- **Text-mode data output is routed to stdout** — ~39 commands across solutions, metadata, plugins, traces, connections, web resources, environments, import jobs, and query history were writing tabular/list data to `stderr`, breaking shell piping and redirection. Data now goes to `stdout`; status, progress, and error messages correctly stay on `stderr` (#1077, #1141).
