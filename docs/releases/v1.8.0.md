## User-visible changes in the candidate

- **Author Main forms through MCP.** Inspect stable form and section IDs, preview adding an existing column, save and verify the unpublished draft, and acknowledge table-wide publication separately. Saving, solution association and publication report distinct outcomes. The bounded tools are list, get, add-field and publish.
- **Keep notebooks bound to the captured environment and account.** Changing focus, defaults or profiles cannot redirect active execution. Results, history, exports and links retain the executed target. A notebook query is not loaded into a Data Explorer panel bound to a different environment or profile. Cancellation affects owned work; per-cell targeting remains outside this release.
- **Opt into bounded data exports.** `data export --max-records-per-entity` sets an optional positive limit on primary rows per entity. Exceeding the limit fails before output is written; it does not silently truncate to the cap. This mode requires paging cookies, and it refuses before exporting a schema with relationships or file, image or binary columns and an entity filter that is not plain `filter`/`condition`/`value` FetchXML. The default remains unlimited.
- **Activate deployed flows explicitly.** Plan and enable or disable one flow or a capped solution selection. Known connection-reference blockers refuse before writes. Results distinguish completed, unchanged, partial, uncertain and unattempted effects. Activation neither rebinds connections nor invokes the flow. `flows list` now pages through all results, and `flows get` refuses a unique name that matches several flows.
- **Preserve form content and make layout changes explicit.** Form XML accepts the known Timeline `UClientActivitiesConfigurationJSON` parameter and legitimate repeated custom-control type IDs while preserving structural and instance-ID validation. New controls use canonical metadata bindings and labels. Repeated add-field requests preserve existing controls in the selected section. Strict field reorder requires a complete permutation; explicit moves preserve cells and reject ambiguous or unsafe spans. `forms add-field` now says when a field it adds already exists elsewhere on the form (`otherPlacements`), and add-field and legacy reorder warn when an existing control's binding differs from the column name only by case (`nonCanonicalBindings`). Those commands do not rewrite existing controls; the new `ppds forms repair-bindings` command rewrites case-variant bindings in a Main form's layout to the exact logical name, changes only those values in the stored XML text, reads the form back to check each change, and previews with `--dry-run`. A repeated placement of a column gets its own control id (`<column>1`, `<column>2`, …, skipping other columns' names) instead of a duplicate, and add-field JSON reports the ids it wrote (`addedControls`; MCP `controlId`). `forms add-subgrid` refuses a generated name that another control already uses as its id.
- **Prevent view reorder from silently removing columns.** `views reorder-columns` requires a complete, case-insensitive permutation and rejects partial, duplicate, unknown or empty lists before writes. Use the separate remove-column operation for removal. Covered view writers acknowledge the resolved target.
- **Reconcile plugin registrations by declared version.** Missing or `1.0` configuration versions preserve omitted optional fields. Version `2.0` reconciles supported nonsecret fields and defaults. Diff preserves `data[]`, states comparison coverage, and distinguishes complete match (exit 0), complete drift (exit 1) and incomplete comparison (exit 12, `Incomplete`); a version 2.0 deploy whose post-deploy verification is incomplete also exits 12. Configured and stored images are paired by name ignoring case everywhere (diff, verification, deploy counts, cleanup, extract), so a case-only difference is a `name` change, not a missing plus an orphaned image. Two configured images on one step whose names are equal ignoring case are refused before connecting (exit 3). An incomplete result is never reported as clean; hidden steps are compared only with `--include-hidden`. A `resetFields` list in the file, or `--reset-fields` on `plugins register step`/`image`, clears named optional fields explicitly. A supplied secure configuration is reported as excluded and does not make the comparison incomplete. On 1.0 and unversioned files, diff still reports a stored step `filteringAttributes` or image `attributes` that the file omits as drift, as CLI 1.4.2 did, with guidance on how to resolve it. Other preserved values are listed in a notice and an additive `preservedLegacyValues` field. Version 2.0 dry-runs list each image that would be deleted, and orphaned-step warnings give the `ppds plugins unregister step <step-id>` command.
- **Respect Dataverse plugin field capabilities and persisted results.** PPDS checks the target's field capabilities. Supported fields can be set on creation; an already-equal non-updatable field is omitted from updates, and a requested mismatch is refused before other mutations without deleting and recreating the step. In the tested PPDS Dev environment, `canUseReadOnlyConnection` was readable and creatable but non-updatable; update requests acknowledged without changing its stored value. Image updates now require readable and writable registration context plus supported optimistic concurrency. PPDS refuses missing capabilities and changed row versions without an unconditional fallback or automatic mutation retry. Direct invocation-source updates now check readback and report nonconvergence instead of treating acknowledgement as proof of persistence. Package downloads use Dataverse file-column content, and package targeting uses checked identities with collision refusal.
- **Preview plugin changes accurately and scope image cleanup.** Existing steps, types and images are distinguished from new registrations in dry-run counts. Version 2 image cleanup requires complete explicit lists on uniquely owned configured steps; an empty list permits clearing that step's images while retaining parents. Ordinary deploy does not imply deletion. No atomic rollback guarantee is added.
- **Distinguish omitted choice values from explicit zero.** Allocate omitted values on copies, preserve supplied values, accept bare labels for global choices, retain publisher/range warnings and expose MCP `validationMessages`. Dry-run numbers remain provisional. Allocation reads unpublished metadata for successive status-reason/local-choice additions; supplied values are preserved. For Choice columns, legacy `--options` accepts bare labels and rejects malformed entries instead of dropping them; on `attribute create` for Choice and Choices columns, combining `--option`, `--options` and `--options-file` is an error.
- **Use global choice names in any casing, and edit options before publishing.** A global choice name that differs from the stored name only by case now works on column create, `metadata optionset <name>`, update, add/update/remove/reorder option, colour and the delete preview. In CLI 1.4.2 it failed as not found. The stored name is looked up only when Dataverse reports the option set as not found; that fault is recognised by its Dataverse fault code (`0x80040217`), with the English server message as a fallback. `optionset delete` shows the stored name and asks for it when it prompts. Just before deleting, it rechecks that the choice is still the one it previewed and refuses if it was renamed or recreated. The recheck and the delete are separate requests, so this is not protection against a concurrent change made between them. Status-reason and choice options added but not yet published can be updated or removed; `--label` targeting is refused when published and unpublished labels disagree.
- **Check the MCP environment allowlist before connecting.** `ppds_env_select` rejects disallowed or malformed URLs before any authenticated resolution, resolves names through discovery only, and rechecks the resolved target before switching. This closes a pre-existing ordering weakness found during release review (SR-01); tool schemas and public signatures are unchanged.
- **Make metadata previews, label updates and errors more accurate.** Five schema-delete families inspect dependency edges and refuse blocked or incomplete discovery; actual deletion reads again. Other previews state which checks they perform and which constraints remain unchecked. Primary-ID and the reviewed State, Status and GUID label paths use bounded updates that preserve server authority. Option-insertion errors expose a typed numeric Dataverse fault code where available while withholding arbitrary server messages and trace details. Web-resource prefix warnings do not rename resources.
- **Set option colours and keep other languages' labels.** `--color` on an existing option now changes its colour; since CLI 1.2.0 it had no effect on existing options. The colour travels with the label write and is read back; an unconfirmed colour fails with `WRITE_NOT_CONFIRMED`. `optionset update` no longer reverts unpublished edits, an update without a new label no longer rewrites the label, and label writes keep other languages' labels (`MergeLabels`). Labels are written in English (LCID 1033), and an update warns (`ENGLISH_LABEL_ONLY`) when the caller's own-language label differs and only the English one changed. Keeping other languages' labels is covered by unit tests only; the live run used an organisation with English alone.
- **Confirm notebook DML in the VS Code extension.** Notebook SQL cells previously ran INSERT, UPDATE and DELETE without the daemon's DML guard. Each DML cell now shows a confirmation naming the target environment and profile and the statement, and runs only after "Execute Anyway" for that statement and target; a declined or refused cell stops the rest of the run. The Data Explorer's dialog shares the same confirmation, a confirmation no longer survives re-authentication, and "Load More" cannot re-run DML.
- **Service the distributed runtime without changing library framework contracts.** Self-contained native CLI and bundled VSIX CLI payloads bundle the serviced .NET 10.0.15 runtime, retaining five native targets and four Extension targets. NuGet/tool framework matrices remain unchanged, including Plugins `net462`. Native Linux requires glibc 2.27; VS Code requires 2.28. These ABI floors do not establish vendor support for an operating system.

## Upgrade and compatibility notes

Existing `-e` meanings are retained. Use `-env` or `--environment` for an unambiguous environment selector. Actual legacy entity/entity-list `-e` use emits one fixed, value-free stderr notice. Uniform environment `-e` and removal of legacy form reorder require CLI 2.0 and at least 90 days after complete stable replacement guidance ships; no calendar removal date has been established. Help no longer lists `-f` for `--output-format` or `-v` for `--verbose` on commands where the command's own option already owns that alias (for example `--force` or `--view`); what each alias selects is unchanged. When `--confirm-env` is required because an environment has no saved type, the error now says it is treated as Production and how to record its type with `ppds env config`.

Legacy `forms reorder-fields` retains authoritative add/reorder/drop behavior and the successful JSON data shape (`section`, `fields`, `message`) during deprecation. **It can still drop unlisted fields.** Repeated field names in the requested list, ambiguous selected-section bindings and silent copying from another section are rejected before writes. An existing selected-section instance can still be reordered while legitimate instances elsewhere remain. Explicit add-field permits intentional placement in another section; its idempotence is section-scoped, not a whole-form uniqueness rule.

Unchanged XML does not mean an operation has no effects. Legacy reorder still sends an XML update. Add-field, strict reorder and move can skip an unchanged XML update while still performing expressly requested solution association or **table-wide publication**. The legacy transition warning stays on stderr; this does not promise that formerly accepted ambiguous inputs continue to succeed.

Plugin secure configuration remains write-only: omission/null preserves it; a supplied non-null value, including an empty string, requests a write. Diff cannot compare a secure value, as in 1.4.2. A supplied value is reported per step as excluded ("supplied but not compared"); it does not make the comparison incomplete and never causes exit 12, and a successful version 2.0 deploy that supplies it exits 0. No secure value is printed. Diff's declared comparison scope excludes package/assembly byte equality, solution membership and Custom APIs. Inspect partial or uncertain results before retrying.

`plugins diff` exit codes change from CLI 1.4.2. 1.4.2 returned 0 (no drift) or 1 (drift), and 2 or higher for errors. Diff now also returns 12 (`Incomplete`) when the comparison is incomplete and the result is unknown, for example hidden steps without `--include-hidden`, an unrecognised property in the registration file, or stored images whose names collide ignoring case with a configured image. Exit 2 remains a general failure and returns an error object with no `metadata`. Scripts can tell the cases apart by exit code: 0 match, 1 drift, 12 incomplete, 2 failure; `metadata.status` (`match`, `drift`, `incomplete`) is also available. Exit 1 still means a completed comparison found drift, including a stored `filteringAttributes` or image `attributes` that a 1.0 file omits. A version 2.0 `plugins deploy` whose post-deploy verification could not be completed also exits 12. Earlier builds of this release used exit 2 for all of these cases; a script that treats exit 2 from `plugins diff`, `plugins deploy` or a schema delete as "could not compare" must test for 12.

A registration file whose step lists two images with names equal ignoring case (commonly a pre-image and a post-image with the same name) used to deploy with exit 0 while the second entry silently overwrote the first. It is now refused before connecting with exit 3 and nothing is deployed. Merge them into one image with `imageType: "Both"`, or give them distinct names. In deploy JSON, an image whose stored name differs only by case is now counted in `imagesUpdated`, not `imagesCreated`, and in diff JSON it is a `modifiedImages` entry with a `name` change instead of a `missingImages` plus an `orphanedImages` entry.

Metadata scripts may see different results from 1.4.2. Legacy `--options` on Choice columns now creates an option for a bare label and fails on a malformed entry; both were dropped before. `attribute create` on Choice and Choices columns fails when more than one of `--option`, `--options` and `--options-file` is given; other column types parse as before. `--label` targeting on update/remove fails when published and unpublished labels disagree; use `--value`. A global choice name that differs only by case is now resolved to the stored name, so commands that failed as not found now act on that choice. This includes `optionset delete --force`, which does not prompt. `optionset update-option`, `attribute update-option` and `entity update-statusreason` with neither `--new-label` nor `--color` now fail with `MISSING_REQUIRED_FIELD` (exit 8) instead of succeeding. A colour read-back failure after a successful write now fails with `WRITE_NOT_CONFIRMED` (exit 2); the same failures used to surface as `OPTION_NOT_FOUND` (exit 8), `Connection.Timeout` (exit 4) or an authentication failure (exit 5). Label updates can print an `ENGLISH_LABEL_ONLY` warning on stderr and add it to JSON `data.validationMessages`.

Notebook SQL cells that contain DML now prompt on every execution, and a declined cell stops the rest of the run. Data Explorer DML from a panel whose profile is not the active profile is refused until that profile is made active.

Custom implementations of the CLI tool assembly's `IMetadataAuthoringService` must adapt: `UpdateTableAsync`, `UpdateColumnAsync`, `UpdateGlobalChoiceAsync`, `UpdateOptionValueAsync`, `UpdateStatusReasonAsync` and `UpdateColumnOptionAsync` now return `Task<MetadataLabelWriteResult>` instead of `Task` (#1604). `IFormService.RepairBindingsAsync` (#1606) has a default implementation, and `AddFieldsResult.AddedControls` (#1601) is additive.

Other output changes scripts may notice:

- With JSON output, `plugins diff` now sets `success` to `false` when the comparison is incomplete (in 1.4.2 a completed diff always reported `success: true`), and adds `metadata` with the status and coverage. `data[]` keeps its shape.
- `plugins deploy --dry-run` now ends with "Dry-run complete (planned, not performed): …" instead of "Deployment complete: …" on stderr, for every registration version.
- Metadata `--dry-run` text says which checks were performed, and its help text now describes the same scope. With JSON output, a dry-run of a metadata write adds a `metadata.preview` object (validation scope, publisher-prefix and target-existence checks, option-value allocation, and `changesPersisted: false`); existing `data` fields are unchanged. A delete `--dry-run` reads deletion dependencies, adds a `preview` object to `data`, and returns exit 10 when a dependency blocks the delete or 12 when the checks are incomplete; a real delete refused for the same reasons, including by the recheck after confirmation, exits 10 or 12 too.
- `flows get <name>` fails with a validation error (exit 3) that lists the matching ids when more than one cloud flow has that unique name. 1.4.2 returned one of them.
- Validating registration files against the updated `plugin-registration.schema.json` may now flag a `version` other than `1.0` or `2.0`, which the CLI also rejects, and undefined properties in version 2.0 files.

CLI 1.5 / MCP 1.3 retain the previously agreed one-release exception for specifically reviewed safety/default and implementation-signature changes. It grants no future compatibility or security waiver. Update the Extension and bundled daemon together; changing account or environment requires deliberate restart or rebind. Full #1015/#1215 parity and per-cell notebook targeting remain excluded.

The finite metadata label-update support is not a universal fallback: EntityName and other unreviewed metadata shapes remain unsupported. Consecutive draft status-reason allocation is covered, but the request to print arbitrary underlying server text is deliberately not implemented; bounded numeric fault identity is the supported diagnostic contract. These distinctions must remain in the individual issue dispositions.

## One-release compatibility exception

On **2026-11-01**, Josh explicitly approved the then-proposed versions and a **one-release exception for CLI 1.5.0 and MCP 1.3.0**. The exception covers the intentional protected-write/session behavior changes and the CLI/MCP implementation-signature incompatibilities listed below. It treats these packages as the documented .NET tools while disclosing the impact on custom embedders.

This decision does **not** declare the release fully backward-compatible, promise binary compatibility for custom embedders, change the general major-version policy, permit future incompatible minor releases, or waive stable-release security/validation gates. The exception does not cover standalone libraries. The later Migration export-limit API and the Dataverse option-presence, `DeleteGlobalChoiceRequest.ExpectedMetadataId` and `MetadataValidationException` inner-exception constructor APIs are additive and are disclosed separately; production strong-name verification remains pending. The approval authorizes release preparation; tags, publication, deployment remain separately held for release authorization. Approved bounded PPDS Dev tests are recorded separately below.

### Script and session migration

- Add `--confirm-env <resolved-url>` to existing protected CLI form- and view-write scripts. Resolve/review the actual target; a mismatched acknowledgement fails before writing. Existing read-only restrictions remain effective.
- MCP form callers supply `confirmEnvironment` when required. `--allowed-env` only authorizes switching. Supply the exact table logical name as `confirmPublishEntity` for table-wide publication and inspect partial/unknown phases before retrying.
- Restart MCP after creating/replacing its startup authentication. External default changes no longer redirect a running session. Allowed in-session switches affect subsequent calls, and `ppds_auth_who` reports that session's target.
- Upgrade the Extension with its matching bundled daemon and restart it when instructed. Missing/mismatched captured identity fails closed. Valid legacy notebook target metadata is retained; notebook target acknowledgement is not DML authorization.
- Replace duplicate form labels/names with stable tab/section IDs. Unique legacy GUID-valued names still work when no true ID matches.

### Custom .NET embedding migration

These are public declarations in the CLI/MCP **tool assemblies**, not new features of the standalone Auth/Dataverse/Migration/Query/Plugins libraries. Consumers embedding those tool types must rebuild/adapt; old binaries are not claimed compatible.

| Contract | Change and required adaptation |
| --- | --- |
| `IWebResourceService.CreateAsync` | Return type changes from `Task<Guid>` to `Task<CreateWebResourceResult>`. Read `Id` and handle `Warnings`; update custom implementations. |
| `FormService` constructor | The three-parameter CLR constructor becomes five parameters with optional confirmation/coordinator arguments. Recompile callers and supply a resolved confirmation service for writes; the no-context fallback deliberately rejects mutations. |
| `FormDetail` positional record | Constructor and `Deconstruct` expand from eight to ten values (`DraftHash`, `State`). Rebuild construction/deconstruction consumers and adapt eight-value deconstruction. |
| `IFormService` | Custom implementations must implement `AddFieldDraftAsync` and `PublishFormEntityAsync`. |
| `IDaemonConnectionPoolManager` | Custom implementations must add `GetOrCreateCapturedServiceProviderAsync`. |
| `IMcpConnectionPoolManager` | Custom implementations must add `GetOrCreateCapturedPoolAsync`. |

The original three-argument `DaemonConnectionPoolManager` constructor remains available; its new interactive-auth-policy overload is additive. Added `FlowInfo` and `ConnectionReferenceInfo` properties are additive. Later additions are also additive: `IFormService.ReorderFieldsWithResultAsync` has a default implementation, `AddFieldsResult` gains `OtherPlacements` and `NonCanonicalBindings`, and `MetadataDeletePreviewResult` gains `TargetName`. None of these details authorizes broad library compatibility exceptions for later releases.
