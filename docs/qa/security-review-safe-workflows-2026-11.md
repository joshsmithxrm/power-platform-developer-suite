### SR-01 — authentication and direct connection preceded MCP target policy (preexisting; corrected in preparation)

At merged product `5e9d5acc7`, `EnvSelectTool.ExecuteAsync` called `EnvironmentResolutionService.ResolveAsync` before `SwitchEnvironmentAsync` checked the allowlist. The authoritative public baseline already had the same order before `ValidateEnvironmentSwitch`; `src/PPDS.Auth` has no diff in this release range. The shared resolver accepts any absolute HTTP(S) URI (and a loose Dynamics hostname heuristic), trims/prefixes it, creates a credential provider, then calls `CreateServiceClientAsync`. It has no PPDS allowlist or host/IP restriction before that direct path. A permitted MCP caller could therefore initiate authentication and organization-metadata connection to a disallowed valid Dataverse organization even when the session refused the eventual switch. Failed direct resolution could also fall back to global discovery for interactive profiles.

This was a confirmed ordering weakness, not a proven arbitrary token-exfiltration exploit. InteractiveBrowser credentials request `<supplied URL>/.default`, key the in-memory token by that exact URL and use the configured Microsoft cloud/tenant authority; they do not blindly reuse the current organization's cached token for a different URL. Client-secret credentials pass the target through an SDK connection string and delegate discovery/authentication to the Dataverse SDK. No claim is made that the SDK rejects every hostile host/challenge, and no live or hostile-endpoint experiment was performed. Before correction, the allowlist enforced final selected-target state rather than all authentication/network activity.

The coordinator implemented `McpToolContext.EnvironmentSelection.cs`: explicit URLs are strictly normalized and policy-checked before direct resolver creation; names use only Global Discovery/BAP metadata, validate the resulting URL, and never connect to the selected organization during name resolution. The final switch rechecks policy after awaits. Independent review also caught exact duplicate display names being selected by the shared resolver's first-match behavior; the MCP-local resolver now refuses multiple exact matches while preserving ID/URL/unique-name/display-name precedence and existing partial-match refusal. Shared Auth/library code is unchanged.

The final offline MCP suite passed **197 tests, 0 failed, 3 existing skips**, including 23 new URL/name/cancellation/captured-profile/final-target cases. The reviewer read the actual source, tests, log and TRX; the coordinator executed this suite. ### Explicit remaining behavioral limits

- Form concurrency can be **preflight-only** when Dataverse does not support optimistic concurrency. Cooperating process locks are not a global transaction across editors. Association/publication can succeed after draft save and before a later failure; inspect the phase results.
- Flow reference metadata does not prove connector credentials, permissions, licensing, DLP compliance or successful future trigger execution. Plan hashes are preconditions, not an atomic server-side transaction, and activation itself may enable triggers. The live fixtures used harmless manual Button/Compose definitions and never invoked them.
- Notebook cancellation evidence proves local execution ownership and result suppression. The live harness delays response delivery at the client boundary; it does not prove a remote operation stopped at a precise instant. Existing cross-environment SQL semantics remain available; a notebook binding is not an authorization sandbox.
- Opaque profile hashes are consistency tokens, not secrets or access-control credentials. The local daemon and MCP process still run with the user's configured authority. Users must treat imported notebooks, MCP instructions and workspace content as untrusted requests and explicitly review intended targets.
- Generic CLI E2E teardown still has an unbounded `WaitForExitAsync(CancellationToken.None)` after a kill attempt (`CliE2ETestBase`). This is a test-harness availability risk, distinct from the bounded flow helper. The Integration workflow aborts a wedged test host with `--blame-hang-timeout 6m --blame-hang-dump-type none`; no shorter explicit job timeout is claimed. The coordinator deferred a separate harness change.

### Publisher and version controls

- NuGet preflight checks exact component/tag/version/source identity, same-commit dependency tags from the actual release graph, framework/assembly inventory and package metadata. Metadata-only assembly inspection checks informational versions and full source SHA. Plugins additionally require the repository's exact public key and a passing native `sn.exe -vf`; public signing alone is insufficient. No private signing key was inspected or used locally.
- Registry queries fail closed on lookup failures and occupied versions. The workflow removes package `--skip-duplicate` behavior. This is a preflight, not an atomic registry reservation; the publication service must still reject a concurrent duplicate.
- Extension preflight binds source manifest/lock, stable/pre-release channel, exact CLI co-tag/source, VSIX manifest and bundled CLI bytes. Publishing uses the **exact validated archive** with `--packagePath`, not a second packaging operation. Per-platform vacancy checks permit only the intended other-platform siblings.
- CLI releases require a source/run-owned draft, exact notes/channel, and expected asset names, sizes and SHA-256 digests. Unknown drafts and changed assets are refused; uploads never clobber. Independent review found the need for a post-upload inventory readback: the final workflow now runs `cli-plan --require-complete` before setting `draft=false`.
- Read-only subprocess checks use explicit argument arrays, no shell, disabled stdin and bounded timeouts. These guards do not make upstream mutable workflow action tags immutable, validate publishing credentials, or prove future registry contents.

The Extension manifest and lock changed only their three version fields to 1.8.0; dependency declarations are unchanged. The runbook now publishes individual tags in verified dependency waves, uses workflow-owned drafts, and requires explicit recovery decisions instead of automatic deletion/retagging.
