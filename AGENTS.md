# PPDS agent guide

PPDS is a .NET and TypeScript developer platform for Microsoft Dataverse: a CLI with a TUI, a VS Code extension, an MCP server and NuGet libraries.
Business logic lives in Application Services (`src/PPDS.Cli/Services/` and the libraries under `src/`); the CLI, TUI, extension daemon and MCP tools are thin adapters over them.

## Rules the code will not tell you

- Put business logic and persistent state in an Application Service, never in UI code: the CLI, TUI, RPC daemon and MCP server must share one code path.
- Do not read or write files from command handlers, screens or tools; call a service. File access in UI code bypasses the shared path.
- Get a pooled Dataverse client inside each parallel branch and dispose it there; one client held across parallel or repeated awaited calls serialises the work and defeats the pool.
- Never construct `ServiceClient` directly; use `IDataverseConnectionPool`. Each new client re-authenticates.
- CLI status and progress text goes to stderr (`Console.Error.WriteLine`); stdout carries only data, so piped output stays parseable.
- Application Services throw `PpdsException` with a code from `ErrorCodes`, not raw exceptions, so every surface can handle errors by code. Keep GUIDs and stack traces out of `UserMessage`. How codes become CLI exit codes is in CONTRIBUTING.md, "Errors and exit codes".
- Accept `IProgressReporter` for any operation likely to take more than a second; services never write to the console themselves, each surface renders progress its own way.
- Pass the `CancellationToken` through every async call, and do not block on async code (`.Result`, `.GetAwaiter().GetResult()`).
- In loops, use the bulk APIs (`CreateMultiple`, `UpdateMultiple`) rather than one request per record, and count with a FetchXML aggregate rather than retrieving records.
- Do not hand-edit `src/PPDS.Dataverse/Generated/`; it is regenerated by `scripts/Generate-EarlyBoundModels.ps1`.

Most of these have a Roslyn analyzer in `src/PPDS.Analyzers` (PPDS001-PPDS013, applied to PPDS.Cli and PPDS.Mcp), but they run at suggestion severity, so the build will not stop you. PPDS015 and PPDS016 (CLI and MCP descriptions) are build errors there. In PPDS.Dataverse, PPDS.Migration, PPDS.Auth and PPDS.Plugins, public API without XML documentation fails the build through the compiler's CS1591 (code under `Generated/` is exempt).

## Build and test

| Surface | Commands |
|---------|----------|
| .NET (CLI, TUI, MCP, libraries) | `dotnet build PPDS.sln -v q`, then `dotnet test PPDS.sln --filter "Category!=Integration" -v q` (tests also need the .NET 8 and 9 runtimes) |
| One test project, SDK only | `dotnet test tests/PPDS.Cli.Tests/PPDS.Cli.Tests.csproj -f net10.0 --filter "Category!=Integration"` |
| TUI logic | `dotnet test PPDS.sln --filter "Category=TuiUnit"` |
| VS Code extension | `npm install --prefix src/PPDS.Extension`, then `npm run typecheck:all --prefix src/PPDS.Extension`, `npm run ext:lint`, `npm run ext:test` |
| Extension end to end | `npm run ext:test:e2e` (downloads VS Code) |
| TUI snapshots | `npm install --prefix tests/PPDS.Tui.E2eTests`, `dotnet build src/PPDS.Cli/PPDS.Cli.csproj -f net10.0`, then `npm run tui:test` |
| Python scripts and CI policy | `pip install pytest pyyaml`, then `python -m pytest tests/ -q` |

`npm run ext:compile` runs esbuild only and does not type-check; always run `typecheck:all` as well.
Unit tests need no Dataverse environment or credentials. `Category=Integration` tests, mostly in `tests/PPDS.LiveTests`, need a live environment and skip themselves without credentials.

## Before you open a PR

CI is the gate: the required checks are `build-status` and `test-status`. A spec is not required for a bug fix or small change. Add or update tests, add user-visible changes to the `## [X.Y.Z] - Unreleased` section of the affected package's `src/<package>/CHANGELOG.md` (not the empty `## [Unreleased]`), and say in the PR what you ran. See [CONTRIBUTING.md](CONTRIBUTING.md) for the full process.
