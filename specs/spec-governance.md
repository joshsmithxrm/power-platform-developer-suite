# Spec Governance

**Status:** Draft
**Last Updated:** 2026-11-18
**Surfaces:** All
**Code:** System-wide

---

## Overview

Spec governance defines how PPDS specifications are named, structured, kept current, and indexed, and when a spec is required at all.

Specs in `specs/` are living descriptions of domain concepts ("what Plugin Traces should be"), not project plans. They are written and maintained mainly during maintainer-led feature work. The rules that govern them sit in Part 2 of the constitution, separate from the architecture principles every contributor follows, so that a bug fix or small change never needs spec work first.

### Goals

- **Clear rules**: The constitution's Spec Process part defines naming, lifecycle, granularity, and acceptance criteria for specs
- **Clear scope**: Spec rules apply when a spec is being written or changed; outside contributors are not asked to write specs
- **Living specs**: Specs evolve with the feature, not frozen after initial implementation
- **Honest index**: README auto-generated from frontmatter, impossible to drift
- **Code-to-spec reconciliation**: `/spec` reads code and updates specs, closing the feedback loop

### Non-Goals

- Spec archival/deprecation policy (deleted = gone, per SL5)
- Automated spec generation from code without human review
- Enforcing spec rules in CI

## Specification

### Constitution Structure

`specs/CONSTITUTION.md` has two parts:

- **Part 1 — Architecture Principles** (A1–A3, D1–D4, I1, I2, I4, I5, SS1–SS2, S1–S3, R1–R3). Applies to all code and all contributors. Violations are defects.
- **Part 2 — Spec Process** (I3, I6, SL1–SL5). Applies when a spec is being written or changed. It opens with a scope statement: a bug fix or small change from an outside contributor does not require writing or updating a spec; if a change affects behaviour a spec describes, the PR says so and a maintainer updates the spec.

I3 and I6 keep their Interface Law IDs although they sit in Part 2, so existing references by ID still resolve. The constitution is the single source of rule text; this spec does not restate it.

### Spec Template

**Frontmatter:**

1. No `**Version:**` line. Version tracking is the Changelog section.

2. `**Surfaces:**` line after `**Code:**`:
   ```
   **Surfaces:** CLI | TUI | Extension | MCP | All | N/A
   ```
   Lists which UI surfaces this spec affects, so verification knows which surfaces need testing.

3. `**Code:**` must be relative path prefixes that can be matched by grep (SL4). Examples:
   - Good: `[src/PPDS.Dataverse/Services/](../src/PPDS.Dataverse/Services/)`
   - Good: `[src/PPDS.Cli/Commands/PluginTraces/](../src/PPDS.Cli/Commands/PluginTraces/)`
   - Bad: `Multiple — see per-panel sections`
   - Bad: `None` (when code exists)

**Changelog section** at the bottom of the spec (before Roadmap if present):

```markdown
## Changelog

| Date | Change |
|------|--------|
| 2026-03-18 | Initial spec |
| 2026-03-20 | Added MCP surface section, updated AC-05 status |
```

This is mechanically appendable by `/spec` during reconciliation. Version numbers that nobody bumps are replaced with a dated record of what actually changed.

**Surface sections within specs:**

When a spec covers a domain concept implemented across multiple surfaces, the Specification section should include surface subsections:

```markdown
### CLI Surface
{CLI-specific commands, flags, output format}

### TUI Surface
{Screen layout, keyboard navigation, filter dialogs}

### Extension Surface
{Panel wiring, webview behavior, VS Code integration}

### MCP Surface
{Tool schema, response format}
```

Only include sections for surfaces where the implementation has meaningful surface-specific behavior beyond what the Application Service provides.

### README Auto-Generation

**`specs/README.md` is an auto-generated file.** It is never hand-edited. `scripts/generate-spec-readme.py` scrapes frontmatter from all `specs/*.md` files (excluding `CONSTITUTION.md`, `SPEC-TEMPLATE.md`, and `README.md` itself).

**Generated format:**

```markdown
# Specifications

> **Constitution:** All specs must comply with [CONSTITUTION.md](./CONSTITUTION.md).
> See Spec Laws (SL1–SL5) for naming, lifecycle, and granularity rules.

<!-- AUTO-GENERATED — do not edit. Regenerated by /spec or scripts/generate-spec-readme.py -->

| Spec | Status | Surfaces | Code | Purpose |
|------|--------|----------|------|---------|
| [authentication.md](./authentication.md) | Implemented | All | `src/PPDS.Auth/` | Authentication, credential management, and discovery |
| [plugin-traces.md](./plugin-traces.md) | Implemented | CLI, TUI, Extension, MCP | `src/PPDS.Dataverse/Services/` | Plugin trace querying, inspection, and management |
| ... | ... | ... | ... | ... |
```

**Generation trigger:** `/spec` runs `python scripts/generate-spec-readme.py` after every spec create, update, or reconcile operation. The script can also be run on demand.

**Frontmatter scraping rules:**
- **Spec name:** filename (linked)
- **Status:** from `**Status:**` line
- **Surfaces:** from `**Surfaces:**` line
- **Code:** from `**Code:**` line, shortened to path prefix only
- **Purpose:** first sentence of the Overview section (after the H1)

### Spec Discovery

To find the specs that govern a piece of code, grep all `specs/*.md` files for `**Code:**` lines and match the code's path against the prefixes. This discovers governing specs without depending on the README index. `/spec` uses this map for overlap checks and cross-references.

### /spec Modes

The `/spec` skill (`.claude/skills/spec/SKILL.md`) has four modes:

- **Create** — spec does not exist; check for overlapping scope, then author from the template
- **Update** — spec exists, user requests changes
- **Reconcile** (`--reconcile`) — align an existing spec with its code
- **Audit** (`--audit`) — read-only check of one or all specs against code, tests, and the constitution

**Reconcile mode behavior:**

1. Read the spec and extract all ACs, Code paths, and type descriptions
2. Read the code at the spec's `Code:` paths
3. Enumerate public types, methods, and behaviors in the code
4. Compare against existing ACs:
   - **Missing ACs:** Code behavior with no corresponding AC → propose new ACs
   - **Stale ACs:** AC describes behavior the code no longer has → flag for removal
   - **Status drift:** AC references a test that now passes/fails differently → update status
5. **Member-count verification:** Count public types/methods in code, count ACs. Report the delta. If ACs cover less than 90% of public surface area, warn explicitly. This prevents the known LLM summarization problem (capturing ~70-80% and missing the rest).
6. Compare spec prose (Architecture, Core Requirements) against actual code structure
7. Present all proposed changes to user for approval before writing
8. After writing, regenerate README and append to Changelog

**Audit mode behavior:** never modifies specs or code. For each spec it checks the AC table (I3), whether referenced tests exist and their statuses are accurate (running single tests with `dotnet test --filter "FullyQualifiedName~..."` or the extension's vitest `-t` filter), code-to-spec alignment, the constitution laws relevant to the spec's type, and contradictions with related specs. Drift found by an audit is fixed with reconcile mode.

**`**Code:**` upkeep:** when work adds code in a new location, the spec's `**Code:**` frontmatter gains that path prefix so discovery keeps working.

### Edge Cases

| Scenario | Expected Behavior |
|----------|-------------------|
| Spec has `Code: None` (Draft, no implementation yet) | Frontmatter grep returns no match for code paths. Spec is still discoverable by name. A Code: path is added when implementation begins. |
| Spec has `Code: System-wide` (architecture, governance) | Frontmatter grep does not match specific code paths. These specs are consulted by name (e.g., `/spec` always treats `architecture.md` as related). |
| Multiple specs govern the same code path | Frontmatter grep returns multiple matches. All matches are considered. This is expected for cross-cutting specs like `per-panel-environment-scoping.md`. |
| `/spec` reconcile mode finds 0 drift | Reports "spec is current" and skips writing. Does not append a no-op Changelog entry. |
| New spec created with `/spec` | Create mode follows the template. README is regenerated. Changelog starts with "Initial spec" entry. |
| Outside contributor's change affects behavior a spec describes | Contributor notes it in the PR; a maintainer updates the spec. The contributor is not required to edit the spec. |

## Design Decisions

### Why Constitution Laws Instead of a Separate Governance Doc?

**Context:** Spec governance rules need to be available wherever specs are written or reviewed.

**Decision:** Keep the spec rules in the constitution rather than a separate governance document.

**Alternatives considered:**
- Separate `GOVERNANCE.md` file: One more file to find and load.
- README.md as governance doc: Wastes the one filename that gets auto-rendered on GitHub, and it is generated.

**Consequences:**
- Positive: One file holds every rule, with stable IDs.
- Negative: Spec procedure sits next to architecture principles. Mitigated by the two-part structure below.

### Why Split the Constitution Into Two Parts?

**Context:** The constitution mixed architecture principles that apply to every change with procedure about spec documents (I3, I6, SL1–SL5). Read as one body of law, it told outside contributors, and their AI agents, that a small feature needed spec work first. Nothing in CI checks the spec rules.

**Decision:** Part 1 holds architecture principles for all code. Part 2 holds spec process, scoped by a plain statement that bug fixes and small contributor changes do not need a spec. Rule IDs and wording are unchanged.

**Alternatives considered:**
- Delete the spec rules: The maintainer still uses the spec system for feature work.
- Move spec rules to a separate file: Breaks references by ID and splits the rule set.
- Renumber I3/I6 as SL rules: Breaks existing references.

**Consequences:**
- Positive: Contributors see which rules apply to them. Existing ID references still resolve.
- Negative: The Interface Laws section in Part 1 has gaps at I3 and I6. A note there points to Part 2.

### Why Auto-Generated README Instead of Killing It?

**Context:** The hand-maintained README drifted (it once listed half the specs on disk).

**Decision:** Auto-generate the README from spec frontmatter.

**Alternatives considered:**
- Kill README and rely only on frontmatter grep: Loses the GitHub-rendered landing page.
- Hand-maintained README with better discipline: Already failed.

**Consequences:**
- Positive: README is always accurate. GitHub landing page preserved.
- Negative: README must be regenerated after spec changes. Mitigated by `/spec` running the script.

### Why One /spec Skill With Reconcile and Audit Modes?

**Context:** Code→spec reconciliation is needed after implementation and for periodic maintenance; drift also needs diagnosing without changes.

**Decision:** Reconcile and audit are modes of `/spec` rather than separate skills.

**Alternatives considered:**
- Separate `/spec-reconcile` or `/spec-audit` skills: Creates ambiguity about which to use, and duplicates the foundation-loading and discovery steps.

**Consequences:**
- Positive: One place for all spec work. Audit stays read-only; reconcile applies the fixes.
- Negative: `/spec` has four modes. Mitigated by explicit flags.

### Why AC Status Tracks Test Results?

**Context:** AC statuses (✅ ❌ ⚠️ 🔲) need updating as implementation progresses.

**Decision:** An AC's Status reflects an actual test result, not implementation intent. Reconcile and audit modes check statuses against tests.

**Alternatives considered:**
- Mark ACs done when code is written: Marks ACs as implemented before tests exist or pass. Creates false confidence.

**Consequences:**
- Positive: AC status is grounded in test results, not self-assessment.
- Negative: Statuses lag until someone runs reconcile or audit. Acceptable — specs are not a CI gate.

### Why Flat Directory Instead of Nested?

**Context:** Specs need organization.

**Decision:** Keep `specs/` flat. No subdirectories.

**Alternatives considered:**
- Nested: `specs/features/`, `specs/core/`, `specs/tools/`: Category arguments waste time ("is this a feature or process?"). Every reference to `specs/plugin-traces.md` would break.

**Consequences:**
- Positive: Simple. All references remain stable. Grep works without recursion flags.
- Negative: Many files in one directory. Manageable with alphabetical naming and the auto-generated README.
