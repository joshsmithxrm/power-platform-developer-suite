# Environment confirmation

**Status:** Implemented; live fixture validation pending
**Code:** src/PPDS.Cli/Services/Environment/ src/PPDS.Mcp/Infrastructure/

## Contract

Selected mutating application services enforce target acknowledgement independently of their surface. Reads and dry runs require no acknowledgement. Read-only sessions reject every write. Effective Production/Test protection requires acknowledgement; Unknown without a configured override fails protected through WriteProtectionResolver. A supplied mismatched URL is always rejected. CLI uses `--confirm-env <url>`, distinct from operation-level confirmation; MCP uses `confirmEnvironment`, distinct from allowed environment switching.

Each operation captures an immutable resolved target, authenticated identity and session. The connection pool and guard use that same target. Acknowledgement is memory-only, scoped to session/identity/target/current policy. Missing context fails closed. Changing an external active profile cannot redirect a running MCP session. Environment switches affect new calls and do not dispose pools used by in-flight calls.

Coverage: every FormService writer, the flow activation service, and all nine existing ViewService writers. Other domains retain their existing guards. This is not a claim of complete #1015 coverage. View CLI acknowledgements are distinct from target selection and entity-wide publication; the original read-service constructor fails closed for writes without context.

### Lowering protection (#1829)

The saved environment type is the main input to write protection besides an explicit protection value, so changing it is itself protected. `EnvironmentConfigService` refuses a change that lowers protection (`Environment.ProtectionLoweringConfirmationRequired`) unless the caller passes a confirmation naming the environment. CLI `env config` asks for the URL to be typed in an interactive run and accepts `--confirm-lower-protection <url>` otherwise; the daemon's `env/config/set` accepts `confirmLowerProtection`, which the extension sends only after its own modal; the TUI dialog asks first; the MCP host registers `ProtectionLoweringPolicy.Refuse` and refuses (`Environment.ProtectionLoweringRefused`). Creating an entry without a type also moves SQL DML on that environment from Production to Development through the SQL rule's own treatment of a missing type; that is #1706 and is not gated here.

**What the acknowledgement protects against.** It stops a script or agent that was refused for an unconfirmed write, or for an unconfirmed lowering, from lowering protection blindly: the refusal names the option but never prints a ready-made command with the address filled in, piped or empty input never counts as an interactive confirmation, and the MCP server refuses the change outright. It does not stop a local process that deliberately sends the acknowledgement, with `--confirm-lower-protection <url>` on the CLI or `confirmLowerProtection` over the daemon's stdio, which any client of the daemon can send: such a process already runs as the user and can edit `environments.json` directly. The acknowledgement is a deliberate act that a reader can see in a script or log, not an authentication boundary.
