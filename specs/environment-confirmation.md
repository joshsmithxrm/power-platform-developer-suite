# Environment confirmation

**Status:** Implemented; live fixture validation pending
**Code:** src/PPDS.Cli/Services/Environment/ src/PPDS.Mcp/Infrastructure/

## Contract

Selected mutating application services enforce target acknowledgement independently of their surface. Reads and dry runs require no acknowledgement. Read-only sessions reject every write. Effective Production/Test protection requires acknowledgement; Unknown without a configured override fails protected through WriteProtectionResolver. A supplied mismatched URL is always rejected. CLI uses `--confirm-env <url>`, distinct from operation-level confirmation; MCP uses `confirmEnvironment`, distinct from allowed environment switching.

Each operation captures an immutable resolved target, authenticated identity and session. The connection pool and guard use that same target. Acknowledgement is memory-only, scoped to session/identity/target/current policy. Missing context fails closed. Changing an external active profile cannot redirect a running MCP session. Environment switches affect new calls and do not dispose pools used by in-flight calls.

Coverage: every FormService writer, the flow activation service, and all nine existing ViewService writers. Other domains retain their existing guards. This is not a claim of complete #1015 coverage. View CLI acknowledgements are distinct from target selection and entity-wide publication; the original read-service constructor fails closed for writes without context.

### Lowering protection (#1829)

The saved environment type is the main input to write protection besides an explicit protection value, so changing it is itself protected. `EnvironmentConfigService` refuses a change that lowers protection (`Environment.ProtectionLoweringConfirmationRequired`) unless the caller passes a confirmation naming the environment. CLI `env config` asks for the URL to be typed in an interactive run and accepts `--confirm-lower-protection <url>` otherwise; the daemon's `env/config/set` accepts `confirmLowerProtection`, which the extension sends only after its own modal; the TUI dialog asks first; the MCP host registers `ProtectionLoweringPolicy.Refuse` and refuses (`Environment.ProtectionLoweringRefused`). Every writer resolves protection by one rule (`WriteProtectionResolver`): an explicit protection value, else the saved type, and an environment with no saved type (no entry, an entry without a type, or type Unknown) is Production, for SQL DML and cross-environment SQL DML as for the confirmation gate (maintainer decision, 2026-11-24). A value that names no member never resolves weaker than Production: `environments.json` is read by member name only (any case), for `type`, `protection` and the `safety_settings` choices, so a number, even one in range such as `"type": 1`, a numeric string or a list of names fails the read of the whole file. Every reader then stops, reads as well as writes: the environment-config commands, `query sql` (SELECT too), the TUI at start-up and for each query, and the daemon's environment and query methods. The CLI commands and the daemon's methods report `Validation.EnvironmentConfigInvalid`, and the gate reports `Environment.ConfirmationPolicyUnavailable` with the same detail. The message names the file by its full path, the entry and the field, lists the accepted names and says to correct the field by hand; no command repairs the file or skips the entry. The resolver, the gate and the SQL DML and Web API guards treat an undefined value that reaches them another way as Production, and the cross-environment guard treats an undefined `cross_env_dml_policy` as `ReadOnly`. The CLI's `env config --type`, its `env type <name>` and the daemon's `env/config/set` take a type by name only, through one check (`EnvironmentTypeNames`). Creating an entry without a type (a label-only or colour-only save, the extension's Add Environment, the daemon's `env/list` tagging) therefore changes nothing, and recording a weaker type on such an entry is a lowering.

**Requirement: no process and no long-lived surface may undo, or fail to see, a raise made elsewhere.** Several processes share `environments.json` (the CLI, the daemon behind the VS Code extension, the TUI, the MCP server), and the daemon and the TUI live for hours. A raise of protection saved by any of them must survive every later write by any other, and every protection decision must be made from the file as it is when the decision is made:
- Every read of the file and every read-modify-write of it (save, remove, update, the de-duplication write while reading, a whole-collection save) holds a cross-process lock: an exclusive lock on the sibling file `environments.json.lock` (`FileShare.None`: a sharing lock on Windows, an advisory `flock` on Linux and macOS that every PPDS process on the same machine takes; it lives beside the file, so it follows `PPDS_CONFIG_DIR`). The lock does not hold, and nothing reports it, where .NET file locking is turned off (`DOTNET_SYSTEM_IO_DISABLEFILELOCKING`), on a network share that does not enforce the advisory lock (SMB/CIFS, some NFS set-ups), or across machines that sync the configuration folder. It is taken after the store's in-process lock, so the two are never taken in the other order. The wait is bounded (`EnvironmentConfigStore.DefaultLockTimeout`, 10 seconds) and then fails with a `TimeoutException` that says nothing was read or changed. A process that dies holding the lock releases it when the operating system closes its handle; the lock file is never deleted.
- The file is written to a temporary file in the same folder and moved over the old one, so a reader sees the old or the new file, never part of one.
- Every protection decision reads the file: `EnvironmentConfigStore.GetConfigAsync` (the lookup of one environment, used by the confirmation gate, `api request`, model-driven apps, SQL DML on the connected environment and `env/config/get`) reads it every time; the TUI reads the whole collection (`ReloadAsync`) for each query and builds the cross-environment label resolver from that read; the daemon's query path does the same. `LoadAsync` stays cached and is used for display only.
- The CLI's assessment before its prompt and its save are separate reads. The save runs the lowering check again on the entry it replaces, under the lock, so when another process changed the environment in between the stricter result wins: a lowering the prompt did not show is refused.

**What the acknowledgement protects against.** It stops a script or agent that was refused for an unconfirmed write, or for an unconfirmed lowering, from lowering protection blindly: the refusal names the option but never prints a ready-made command with the address filled in, piped or empty input never counts as an interactive confirmation, and the MCP server refuses the change outright. It does not stop a local process that deliberately sends the acknowledgement, with `--confirm-lower-protection <url>` on the CLI or `confirmLowerProtection` over the daemon's stdio, which any client of the daemon can send: such a process already runs as the user and can edit `environments.json` directly. The acknowledgement is a deliberate act that a reader can see in a script or log, not an authentication boundary.
